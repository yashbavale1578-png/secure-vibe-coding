# Identity, sessions, authorization, and secrets

## Secrets
- Separate public configuration from secrets. A value is not safe merely because it is called an API key or environment variable.
- Use the secret manager provided by the deployment platform where practical. Limit read permissions and scope credentials per service/environment.
- Keep privileged database keys, signing keys, OAuth client secrets, payment secrets, and AI provider keys on trusted server-side components.
- Treat public/client keys as public. Enforce authorization independently using provider-supported RLS/policies.
- Scan current files and Git history. If a credential was committed, assume compromise: revoke/rotate first; history rewriting is not a substitute for revocation. Coordinate force-pushes with collaborators.
- Redact secrets in reports and logs. Never paste a secret into a model prompt, issue, chat, or generated report.

## Passwords and authentication
- Prefer a maintained identity provider when it meets the requirements.
- If storing passwords, use a dedicated password hashing library and Argon2id where supported. Use library-recommended current parameters; benchmark appropriately and re-check guidance over time.
- Use unique salts generated by the library. Do not use fast general-purpose hashes such as SHA-256 alone for password storage.
- Reset tokens should be random, single-use, time-limited, stored safely (typically hashed), and invalidated after use.
- Avoid account enumeration in login, registration, and password reset responses where appropriate.
- Use MFA for administrators and sensitive operations when feasible.

## Sessions and cookies
- Rotate session identifiers after authentication and privilege changes.
- Invalidate sessions on logout, credential reset, account compromise, and relevant privilege changes.
- Set Secure on HTTPS-only cookies, HttpOnly for session identifiers, and an appropriate SameSite policy. Choose Domain, Path, and lifetime narrowly.
- CSRF controls are still required where the authentication model and browser behavior make cross-site requests possible. SameSite is defense-in-depth, not a universal replacement.
- Avoid storing session tokens in browser local storage when a safer server-managed session design is practical.

## Authorization
- Check authorization on every server-side request and every object/action boundary.
- Verify object ownership and tenant context from trusted server-side identity, not user-supplied IDs alone.
- Deny by default. Keep roles and permissions narrow.
- Prevent mass assignment: explicitly allow fields users may change.
- Test as different roles and tenants, including unauthenticated, expired, suspended, and least-privileged users.
- Database RLS is defense-in-depth and must be tested for SELECT, INSERT, UPDATE, DELETE, joins, RPC/functions, service-role bypass, and edge cases.
